# Security and Environment Guardrails

## 1. Purpose

This document defines security, secrets, token handling, and environment variable rules for the Social Media Scheduler MVP.

## 2. Environment Variables

## App

```txt
NODE_ENV
APP_BASE_URL
FRONTEND_URL
API_PORT
SESSION_SECRET
TEST_USERNAME
TEST_PASSWORD_HASH
WORKER_SECRET
```

## Database

```txt
DATABASE_URL
DIRECT_URL
```

Rules:

- `DATABASE_URL` is for runtime.
- `DIRECT_URL` is for migrations.
- Runtime code must not use `DIRECT_URL`.

## Backblaze B2

```txt
B2_APPLICATION_KEY_ID
B2_APPLICATION_KEY
B2_BUCKET_NAME
B2_ENDPOINT
B2_REGION
```

## Social Platforms

```txt
META_APP_ID
META_APP_SECRET
META_REDIRECT_URI

LINKEDIN_CLIENT_ID
LINKEDIN_CLIENT_SECRET
LINKEDIN_REDIRECT_URI

TIKTOK_CLIENT_KEY
TIKTOK_CLIENT_SECRET
TIKTOK_REDIRECT_URI
```

Only add variables for platforms actually being implemented.

## Token Encryption

```txt
TOKEN_ENCRYPTION_KEY
```

Used to encrypt social access tokens and refresh tokens before database storage.

## 3. Secret Handling Rules

Do not commit:

- `.env`
- `.env.local`
- Railway secrets
- Vercel secrets
- B2 credentials
- OAuth app secrets
- Token encryption keys

Do not expose to frontend:

- B2 application key
- B2 secret key
- Platform client secrets
- Access tokens
- Refresh tokens
- Worker secret
- Token encryption key

## 4. Auth Rules

MVP uses a temporary single-user login.

Rules:

- Store password hash, not plain password.
- Use HTTP-only cookies.
- Use secure cookies in production.
- Use same-site cookie protection.
- Do not store session tokens in localStorage.

## 5. Social Token Rules

Social access tokens and refresh tokens must be encrypted before being saved.

Never log:

- Access token
- Refresh token
- OAuth authorization code
- Full callback URL if it contains sensitive params

When storing platform responses, sanitize sensitive values.

## 6. B2 Upload Rules

- Frontend must never receive B2 master credentials.
- Frontend can receive presigned upload URL only.
- Object keys must be generated by backend.
- Validate file type and size before presigning.
- Do not allow user-controlled arbitrary object paths.

## 7. Worker Endpoint Rules

If Railway cron calls an API endpoint, it must include:

```txt
X-Worker-Secret
```

Backend must reject missing or invalid worker secret.

## 8. CORS Rules

Allow only known frontend origins.

For local development:

```txt
http://localhost:3000
http://localhost:5173
```

For production:

```txt
https://your-vercel-domain.vercel.app
https://your-custom-domain.com
```

Do not use wildcard origins in production.

## 9. Logging Rules

Safe to log:

- IDs
- Statuses
- Platform name
- Error code
- Timestamps
- Retry count

Do not log:

- Secrets
- Tokens
- Password hashes
- Signed URLs if they grant private access
- Full OAuth callback URLs

## 10. Database Safety

- Use Prisma parameterized queries.
- No unsafe raw SQL with user input.
- Use bounded list queries.
- Use `select` by default.
- Keep external API calls outside DB transactions.

## 11. Production Readiness Checklist

Before production use:

```txt
[ ] All secrets are in Railway/Vercel env vars.
[ ] No .env file committed.
[ ] Cookies are HTTP-only.
[ ] Production cookies are secure.
[ ] CORS is restricted.
[ ] Worker endpoint requires secret.
[ ] B2 credentials are backend-only.
[ ] Social tokens are encrypted.
[ ] Logs do not expose tokens.
[ ] OAuth callback URLs are correct.
```
